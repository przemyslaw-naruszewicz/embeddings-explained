Semantic clustering · the meaning layer

Five newsrooms.
One story.

An embedding is a vector: a fixed-length list of numbers that a language model computes for a piece of text. Texts with similar meanings usually produce vectors that lie close together, so the system can calculate how similar the texts are rather than rely on a reader’s judgement.

When a president resigns, for example, five newsrooms report the event in five different ways. The articles may share no phrasing at all, and sometimes they are not even written in the same language. A program that groups them by common words will miss even a simple paraphrase.

The system represents each article as a point in a semantic space. It does not measure ordinary distance between the points. Instead, it compares the directions of their vectors using the cosine of the angle between them. The resulting score estimates whether the texts are related.

The topic group an article belongs to has its own row in the database and lasts longer than a day. A new report is compared with the centres of existing groups rather than with every other article. A PostgreSQL database with the pgvector extension performs that search.

Primer

Meaning expressed as coordinates

Three properties make embeddings useful for this task.

01

A text as 768 coordinates

An embedding model turns a sentence into a list of 768 numbers. The result is neither a summary nor a set of keywords. These numbers are coordinates that place the text in a semantic space shared by every other text.

02

Nearby vectors suggest related texts

Texts about the same event often land in nearly the same place even when they use different words. Cosine similarity measures that closeness using the angle between their vectors; the card below, “How that score is computed”, works through the whole calculation. This removes the need to write separate rules for synonyms and word order.

03

The same text always gives the same numbers

Computing an embedding is deterministic: the same version of the model returns exactly the same vector for the same text. The result does not depend on when it is computed or on any text processed earlier. Storing the result avoids repeating the calculation.

How that score is computed

The measure from point 02 is the cosine of the angle between two vectors — the same cosine similarity whose scale carries the 0.70 threshold. A vector is a list of numbers; this example uses two coordinates instead of 768 so the whole calculation fits in one diagram. A and B were chosen for the example; they are not model outputs. Both arrows start at [0, 0]: the first coordinate says how far to move the arrow’s endpoint horizontally, the second how far to move it vertically. The angle itself is never needed — its cosine follows directly from the arrows’ coordinates.

1 · Read the coordinates

A = [1, 0]: 1 to the right and 0 upwards.
B = [0.8, 0.6]: 0.8 to the right and 0.6 upwards.

2 · Calculate direction similarity
cos(θ)= A · B|A| × |B|
A · B is the dot product: multiply matching pairs, then add the results. |A| and |B| are the lengths of the arrows. Both must be greater than zero because division by zero is undefined.
1
Calculate the numerator. Multiply numbers in matching positions, then add: (1 × 0.8) + (0 × 0.6) = 0.8
2
Calculate the vector lengths using the Pythagorean theorem: square each coordinate, add the results and take the square root: |A| = √(1² + 0²) = 1
|B| = √(0.8² + 0.6²) = √(0.64 + 0.36) = 1
3
Divide the numerator by the product of the lengths. This removes the effect of arrow size, leaving a comparison of direction: 0.8 ÷ (1 × 1) = 0.80
0.80 The score of 0.80 describes similarity of direction. It does not mean an 80% probability that the texts describe the same event. The “Topic groups” section uses this measure to match an article to a group.
−1 · opposite0 · perpendicular1 · same direction

The diagram shows an angle of about 37° because arccos(0.80) ≈ 37°. The system does not need the angle itself. It uses the score of 0.80 directly when comparing texts.

The technical side

The model used here produces vectors with 768 coordinates. To calculate the dot product, the program multiplies 768 pairs of numbers and adds the results. Ollama’s /api/embed endpoint returns vectors normalised to length 1 (L2 normalisation), with possible small deviations due to numerical precision. For vectors of length 1, the denominator is 1, so the cosine equals the dot product. The full formula also works for vectors of other, nonzero lengths.

A reference point

Why counting words isn’t enough

Before embeddings became common, texts were often compared using TF-IDF. The method first counts words, then gives each one a weight based on how often it appears in a given text and how rare it is across the collection. It considers two texts similar when they contain the same high-weight words.

How TF-IDF compares texts

Two quantities determine the weight of each word: how often it occurs in this text and how rare it is in all the others. A word present everywhere, such as “and” or “is”, does not distinguish one text from another and gets a weight near zero. A rare word, such as “resignation”, gets a high one.

A text becomes a list of such weights, and the similarity of two texts is a measure of how much the two lists overlap. The method uses arithmetic on word counts rather than a language model or machine learning. It fits in a few dozen lines of code and runs without any preparation.

Where it breaks down

Two texts may say the same thing in different words. “The president steps down” and “Macron resigns” share no meaningful word, so their similarity is exactly zero.

To match those two sentences at all, you have to add a list of synonyms, a way of reducing words to their base forms, and a list of names. Someone has to prepare these by hand and repeat the work for every language.

The hardest case: several languages at once

The same event may be covered in English, French and Polish at the same time. If two articles in different languages share no words, a word-counting method assigns them a similarity of zero even when they describe the same event. Without additional rules, everything would first have to be translated into one language. That would require another model, whose errors would also affect the results.

Inflected languages make it worse: three grammatical forms of one Polish noun are three different words to a word counter. A multilingual model can compare texts without separate rules for every language. Because it learned many languages at once, it maps texts from all of them into one shared space. A Polish sentence can therefore land close to its English counterpart.

Neither method is better in every case. Search engines usually combine them: word matching handles a statute number well, while embeddings capture the meaning of a question. Here the task is to decide whether the articles describe the same event, so their meaning matters most.

Why only one method remained

At first, a setting determined the grouping method: development environments without access to the model used TF-IDF, while production used embeddings. As a result, the same batch of articles formed different groups on a developer’s machine and in production, while one similarity threshold had to serve two different distributions of scores. When article groups produce signals that may inform investment decisions, “I got a different result” stops being a minor detail.

Word counting had one advantage: it did not depend on the model. That advantage disappeared after embeddings for the test dataset had been computed once and stored in a fixture alongside the code. Before each test, those vectors are loaded into the cache. Tests therefore use the same embeddings and the same grouping method as production without having to call the model.

Model and infrastructure

What computes these numbers, and where does it run?

The model had to support multiple languages, fit on the same server as the database and application, and run on private infrastructure without sending text elsewhere.

nomic-embed-text-v2-moe

This open model takes text and returns 768 numbers. It does not hold conversations, summarise text or answer questions.

The MoE in the name stands for mixture of experts: the model contains several specialised subnetworks but activates only some of them for any given piece of text. It can therefore provide the capabilities of a larger model while using about as many resources as a smaller one.

For this task, multilingual support matters most: a French wire story and its English write-up can map to nearby points in the space, without translation or hand-written rules.

? What is Ollama?

Ollama is a program that runs language models on your own computer or server. You install it once and download a model with a single command. The model then runs at a local address, much like a database that receives requests and returns results.

Ollama takes a list of texts and returns a list of vectors. The application calls it over HTTP only when a new result has to be computed. No text leaves the server, and local calls are not billed individually.

$ Requirements for running it

A model this size takes ~1.3 GB of memory, and only while a batch is being computed. It fits next to the database and the application itself on an ordinary VPS costing a few euros a month. It requires neither a graphics card nor an account with a cloud provider.

A server may have 4 GB of memory and no swap. In that configuration, the model is unloaded from memory immediately after each batch, and texts are sent to it three at a time. Reloading takes a few seconds and is needed only when a batch contains new content.

The technical side

POST /api/embed, input in chunks of 3, keep_alive: 0 on the last chunk (releasing memory). Address and model name come from configuration (OLLAMA_EMBED_MODEL).

The route

Where embeddings fit into the process

An article passes through six steps on its way from a news feed to a signal. Only two need an embedding. The others reduce the number of model calls and help ensure reliable results.

Steps 01 to 03 do not analyse meaning: the first compares characters, the second looks for words from a list, and the third assembles the text for the model. Semantic analysis begins at step 04. Its result is stored as a row of numbers and used in step 05, where the database points to the group with the nearest centre. Step 06 receives a group with its new articles rather than a vector.

≡ Intake (step 01): has this text been here before?

The same wire copy may arrive from two feeds, or return after a dropped connection. A checksum detects it. This short string is computed from the entire text: the same text always produces the same checksum, while any change produces a different one. If the checksum is already in the database, the article is not stored again.

The check is binary and completely blind to meaning: moving a single comma produces a different checksum and a second row in the database.

≈ Embedding and grouping (steps 04 and 05): is this the same story?

Five newsrooms describe one event in five different texts, so each checksum will be different. Embeddings let the program measure how close those texts are and group them even when they do not share a single sentence.

Each question needs a different tool. The program first compares content checksums, a fast operation that requires no model. Only texts that pass this stage get a vector and are compared with the centres of groups the database already holds. A Tuesday report can join a group opened on Monday, keeping the same group id.

01

Accept it, but only once

Articles sometimes arrive from news feeds more than once. A duplicate may result from a retry after a timeout or from the same wire copy appearing in two feeds. In both cases the content checksum is identical, so the program rejects the second copy.

The technical side

WorldEvent · an identifier computed from the headline and body determines whether an event has already been seen. It uses a fast, non-cryptographic hash function (xxh128(title + content)). This is the deduplication key, deliberately a different one from the key the embedding cache uses.

02

Remove what is clearly irrelevant

A simple keyword filter comes next. It checks for required and disqualifying words, and optionally for trusted sources. It needs no model and reduces the number of texts passed to the stage that uses the model.

If no keywords are configured, nothing gets through. Passing every text in that case could hide the configuration mistake until the bill arrived.

The list still has to be prepared. A large language model can help during configuration, but it is not used during processing. The operator describes what they are looking for, and the model drafts a list of variants, related forms and equivalents in the source languages. The operator reviews and approves the final list.

The technical side

WorldEventFilter → WorldEventFilterSpec: a CPU-only regex gate. When its configuration is empty, it rejects every text instead of allowing all of them through. A group is analysed once, not once per article, so five reports of the same event require one analysis in total. Grouping therefore also reduces the work at the final stage. The result is either a trading signal or an indication that a longer process has moved to its next stage.

Storing the answers

How the model’s results reach the database

The cache stores each computed vector so the model does not have to compute it again. A single class manages the cache and sends the model texts that have no stored vector.

Check the cache before computing

The program calculates a checksum for every text, as it does when catching duplicates, but bases this checksum on what the model actually sees. It then sends the checksums for the entire batch to the database in one query and asks which ones are already known.

Only the remaining texts go to the model. Each result is stored before it is used. When the same text appears again, the program reads its vector from the database instead of running the model a second time.

The pattern: a decorator

The class that queries the database cannot compute an embedding. The class that computes one knows nothing about the database. Both expose the same interface, so the database-aware class can wrap the model class. That is the decorator pattern.

The rest of the program asks for vectors without needing to know whether they came from the database or the model. The cache can therefore be removed, replaced or extended with another layer without changing the code that uses it.

The decorator in code

This shortened version omits logging, the response-length check and the handling of texts repeated within one batch. 

final readonly class CachedTextVectorizer implements TextVectorizerInterface
{
    public function __construct(
        private TextVectorizerInterface $inner,   // the model (Ollama)
        private EmbeddingStoreInterface $store,   // the embedding_cache table
        private string $modelId,
        private bool $ollamaEnabled,
    ) {}

    public function vectorize(array $texts): array
    {
        $hashOf  = array_map(self::keyFor(...), $texts);
        $vectors = $this->store->getMany($hashOf, $this->modelId);   // 1 query

        $misses = $this->collectMisses($texts, $hashOf, $vectors);

        if ([] !== $misses) {
            if (!$this->ollamaEnabled) {
                // a missing vector is an error; never silently fall back to another method
                throw new \RuntimeException('Embedding cache miss …');
            }

            $fresh = $this->inner->vectorize($misses);      // the only call to the model
            $this->store->putMany($fresh, $this->modelId);  // stored before it is used
            $vectors += $fresh;
        }

        return array_map(static fn (string $h) => $vectors[$h], $hashOf);
    }

    public static function keyFor(string $text): string
    {
        return hash('sha256', trim($text));   // keyed on the text the model reads
    }
}

The database key is the pair (text checksum, model name), while the row contains the vector as jsonb. No expiry date is needed because the value does not change.

Text already known

any mode

When the same text appears again, the program reads the numbers from the database without running the model.

New text, model available

The model runs the computation locally, three texts at a time. The result is stored immediately, so the model will not be needed for that text again.

New text, model switched off

backend disabled

The technical side

Table embedding_cache, composite key (sha256(trim(text)), model_id), vector as jsonb, no TTL. Writes use ON CONFLICT DO NOTHING, so parallel workers don’t collide. The model name is part of the key: once it changes, the same text no longer matches the old rows and the vector is computed afresh. The previous model’s vectors stay in the table but are no longer read, so correctness does not depend on anyone remembering to clear the cache. Setting: OLLAMA_ENABLED. Cache initialisation: bin/console app:embed:warm --days=1.

Topic groups

How an article joins a topic group

A topic group is a set of articles that the system has identified as reports about the same event. When another article arrives, the program must decide whether to add it to a known group or start a separate one. It uses embeddings, the numerical representations of those texts, to make that decision.

What is a group’s centre?

Each article has a vector of 768 numbers. To get one vector for the whole group, the program averages each position separately: first the first number from every article, then the second, and so on. The result is another list of 768 numbers. This is the group’s centre.

The centre is a shared reference point for the group. The program compares the new article’s vector with it. For a group with one article, the centre is that article’s vector; with two, it is their average.

Where pgvector helps

The model turns text into numbers. pgvector, a PostgreSQL extension, stores those numbers and compares vectors directly in the database. Here, the database compares the new article’s vector with the stored group centres and returns the closest matches.

The program then checks whether the best match is similar enough. Finding the most similar group does not, by itself, mean the article belongs there.

The technical side

In the database this topic group is called a cluster: it searches world_event_clusters. It includes only this customer’s groups with a report from the last 14 days and vectors from the same model. It computes the distance to every qualifying centre, without an approximate index, and returns up to five nearest matches. The program checks the best result. Group Z, whose last report was 16 days ago, does not qualify, so the query below returns only A.

Centres are stored in the centroid column of type vector(768). The <=> operator returns cosine distance. The program converts it to similarity: 1 − distance. Here the database returns 0.5990, giving 1 − 0.5990 = 0.4010. The program’s code defines the 0.70 threshold.

-- step 2 for headline B1, casts omitted; other customers' rows are cut by the RLS policy
SELECT id, centroid <=> :vector AS distance
FROM world_event_clusters
WHERE embedding_model_id = :model AND last_seen_at >= :today_minus_14_days
ORDER BY centroid <=> :vector
LIMIT 5;

How the centre moves

When an article joins, the centre moves towards its vector. The more articles a group has, the less weight each new report carries in the average. Computing the new centre requires only the old centre, the article count and the new vector.

The technical side

A two-coordinate example, using the same vectors as the “Primer” section. The group has one article, so its centre is that article’s vector A = [1, 0]. Article B = [0.8, 0.6] arrives. Its similarity to the centre was calculated earlier: 0.80.

1 · Old centre, new article, new centre

The new centre is exactly halfway between the two vectors because both have a weight of ½. With ten articles, a new vector would move the centre only one eleventh of the way.

2 · Calculate the new centre
centre′= n × centre + Bn + 1
1
Check the threshold. B scores 0.80 against the centre, which is at least 0.70, so B joins the group.
2
Substitute n = 1, because the group had one article: (1 × [1, 0] + [0.8, 0.6]) ÷ 2 = [1.8, 0.6] ÷ 2 = [0.9, 0.3]
3
The count rises to 2 and the date of the latest report moves to today. The new centre has length √(0.81 + 0.09) ≈ 0.95, less than 1. Cosine similarity still works because the formula divides by the vector lengths.
[0.9, 0.3] The new centre is the average of both vectors. The database updates it together with the article count in one statement, so concurrent joins do not overwrite each other’s result.

In the group table the vectors have 768 coordinates, and the same UPDATE statement does this for all 768 at once.

How topic groups behave

One group across many days

a single identity

A Tuesday report joins the group opened on Monday. The program analyses that same group under its existing id; nothing new is created.

A second run on the same day

no new articles

The program does not analyse a group again unless it has new articles.

A group quiet for 14 days

outside the window

It returns as a new group. That is deliberate: a crisis in March and one in October produce similar vectors, yet for a market signal they are two situations with different opening prices.

The 0.70 threshold still needs validation for matching an article to a group centre. Two concurrent runs for one customer can open the same group twice and trigger an extra analysis.

Choices

Four design decisions

01 Two checksums instead of one

Every article carries a content checksum used to recognise duplicates. Both checksums are built from the headline and body, but the content checksum cannot safely serve as the cache key. If the text sent to the model were assembled differently, the duplicate checksum would stay the same even though the model would read something else. The cache would then return numbers computed from a different text without warning. A second checksum takes only a few lines of code and prevents that mistake.

02 Stopping instead of falling back

If the program fell back on word comparison whenever the model was unavailable, it would still return plausible-looking groups. They would be arranged differently, however, and nothing in the output would reveal which method produced them. Here, article groups produce signals that may later inform a trading decision made outside the application. Incorrect grouping can therefore produce an incorrect signal. It is safer to stop with a clear message than to let a change in result quality go unnoticed.

03 One grouping method in every mode

A setting controls whether the program may call the model; it does not change the grouping method. Tests and offline runs use results stored alongside the code and follow exactly the same path as production.

The technical side

OLLAMA_ENABLED determines whether the model may be called when the cache has no result; it does not select the grouping strategy. The fixture tests/fixtures/embeddings/nomic-embed-text-v2-moe.json is seeded into embedding_cache before every scenario. All three modes call CachedTextVectorizer.

04 Two vector stores, two different questions

The cache checks whether a text already has a computed vector by looking up its exact key. It stores vectors as plain JSON. A similarity index would need updating on every write but would never be queried. A fixed vector size would also prevent the cache from holding results from several models at once.

The topic-group table uses a vector column from pgvector to find the nearest group.

Further applications

What else embeddings can do

Every use listed here relies on the same mechanism as grouping news reports. The model places content in a shared space, and the system compares the resulting vectors with a simple mathematical operation.

what Proximtype does

Grouping and topic discovery

Texts without assigned categories form clusters, each representing one topic, including topics that nobody anticipated.

what Proximtype does

Matching across languages

Reports in French, English and Polish can land in one group without prior translation.

common

Semantic search

A model places queries and documents in the same space, so a search for “what can I do if my purchase is broken” can find the “returns policy for faulty goods”, even though the two phrases share no words.

common

Providing context to a model (RAG)

Before the question reaches a large model, the system attaches passages from the organisation’s own documents, selected for their similarity to the query. The model can then base its answer on that material instead of relying solely on its own memory.

common

Duplicates that aren’t identical

This may be a reposted listing with a changed phone number or the same case submitted a second time in different words. A checksum will treat the two as distinct, but an embedding can help link them.

common

Classification without training

One sentence describes each category. The system assigns a text to the category with the nearest description. Adding a category requires one more sentence rather than another round of data collection and classifier training.

common

Recommendations and “more like this”

The system finds the nearest neighbours in the space and uses them to suggest similar articles, products, job ads or tickets without a hand-maintained taxonomy.

common

Routing support tickets

A new ticket goes to the team whose past cases sit closest to it. The system uses that history rather than a set of rules.

common

Spotting the odd one out

A text lying far from everything the system has seen so far is either irrelevant noise or the first sign of something new. Either way, it is worth a look.

✕ What an embedding will not do

It does not establish whether two texts are identical. The content checksum in step 01 does that. The similarity score is not an explanation either: it shows that two texts are close but not why. The model can use only patterns learned from its training data. For an event from last week, the embedding represents only what appears in the input text.
